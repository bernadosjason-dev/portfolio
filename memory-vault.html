System · methodology

An AI assistant that doesn’t start from zero every session.

A chat model forgets everything the moment the window closes. The Memory Vault is the fix: a plain-text knowledge base, one fact per file, that an assistant reads at the start of a session and writes to during it — so what was learned in one conversation is still there in the next.

01

The problem it solves

Why it exists

Every session, the same ground gets re-covered: which markup the estimators use, why a supplier was dropped, what a client already agreed to. Re-explaining it is slow, and the parts that don’t get re-explained get lost.

Memory has to be a file, not a feature. Kept as plain Markdown in a folder, it’s readable without the AI, searchable in any editor, portable between tools, and diffable in version control. Nothing is trapped in a vendor’s database.

02

Five folders, one job each

Structure carries meaning. Where a note lives tells you what kind of thing it is, which is what lets an assistant file correctly without asking.

Decisions/A choice that was made, with the reasoning and the option that was rejected.dated · immutable
Ideas/Anything raw and unresolved. No polishing. Links forward to a Decision if one gets made.dated · immutable
Business/Current state of the work — what’s running, what’s stuck, what’s next — plus the assets it produces.persistent · edit in place
Prompts/Reusable prompts and templates. The instrument, kept separate from its output.persistent · edit in place
Transcripts/Raw session logs, unedited, for when the summary isn’t enough.dated · immutable

Dated folders accumulate and stay as written — a decision from three months ago is still a record of what was decided then. Persistent folders are living state: edited in place, never forked into a v2.

03

Anatomy of a memory

One fact per file. Frontmatter drives recall; the body is written for a person, and links out to whatever it touches.

---
name: estimator-markup-is-unvalidated
description: The x1.15 / x1.30 markups in the estimators were
             chosen, not tested against real win-rate data
metadata:
  type: project
---

The estimating tools apply a x1.15 markup to sheet goods and
x1.30 to hardware. Those numbers were picked at build time, not
derived from outcomes. Until the [[lead-pipeline-tracker]] has
~25 logged quotes, there is no basis to say whether they are
too high or too low.

Why it matters: quoting is where the margin is set. A wrong
multiplier loses jobs on price or wins them too cheaply, and
neither shows up without the outcome data.
name
A stable slug. It’s how other notes link here, so it doesn’t change.
description
One line. This is what the assistant scans to decide if a memory is relevant to the task in front of it.
type
What kind of fact — user, feedback, project, or reference. Steers how it’s used.
[[wikilink]]
Connects this fact to the tool it constrains. Follow the links and the reasoning reconstructs itself.

05
Rules the assistant follows

    
    
      
  • File on write, not on request. When a decision or a state change surfaces mid-conversation, it gets filed then — not when someone remembers to ask.
    • 
      
  • Deliverables are files. A script, a prompt, a rate sheet — written to a note and treated as the artifact. Chat output alone doesn’t count.
    • 
      
  • Every follow-up gets a deadline. No open-ended “someday” items. If none is given, one is proposed.
    • 
      
  • Cross-link. An idea that becomes a decision links to it. A decision that changes the state of the work links to the updated note.
    • 
      
  • Don’t invent facts into client-facing work. Prices, lead times, warranty terms come from the human. Unconfirmed lines are marked, not guessed.
